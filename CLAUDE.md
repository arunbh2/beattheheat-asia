# CLAUDE.md: Common Shade (beattheheat.asia)

## What this is
A free, open, non-commercial evidence platform on extreme heat in South and Southeast Asia. Common Shade was first published as BeatTheHeat.Asia and is moving to commonshade.asia. It covers:
- an interactive map of consequences, vicious cycles and levers
- a solutions library, funders and funding, and city and country pages
- simulations, a planning workbook (/plan/) and an India heat action plan archive
- /llms-full.txt for AI systems

Counts are calculated from data at build time. Never type a count into a page; read the current numbers from the build output. Readers are city officials, health workers, unions, NGOs, funders and researchers, many of them on low-end Android phones and slow networks.

## The first rule
Every decision elevates the reader's experience (UX), the maintainer's experience (DX) and the AI agent's experience (AX) at once, without breaking anything. A change that helps one at the cost of another is not finished: for example, a feature that adds weight to the homepage for a page most readers never open, a check whose failure does not say what to fix, or page text that differs from what llms-full.txt says. Test what already works before shipping.

## Hard rules
1. **Zero budget.** GitHub Pages only: no paid APIs, servers, databases or accounts.
2. **No new dependencies without asking.** Pages are plain HTML, CSS and vanilla JS. The Node scripts in `tools/` generate the pages, and the output is committed. Ask before adding any library to pages or tools.
3. **Privacy first.** Visitor input stays in the browser (localStorage or the URL). Already in use, and nothing else without asking:
   - Google Fonts
   - GoatCounter, cookieless analytics (`SITE_ANALYTICS` in data.js)
   - Open-Meteo and data.gov.sg (live heat)
   - Europe PMC (recent papers on /news/, a fixed search in `news.js`)
   - Microsoft Forms (the join form embed on /join/)
   Change `/privacy/` (`tools/build-privacy.js`) in the same pull request as any change to these.
4. **Every claim needs a checked source.** Never invent statistics, studies, URLs or quotes. Label illustrative numbers "illustrative". The session has no open internet, so verify links on GitHub with `verify-urls.yml` or `verify-sources.yml` (Europe PMC for publisher pages that block bots). A research batch stages its sources in `data/inbox/<batch>/`, runs `verify-sources.yml` with `month: <batch>`, and lets a claim reach a page only when every term it rests on was found; a page that only opened is not evidence.
5. **Humble, diplomatic voice.** The aim is awareness, blind spots and solutions, never blame.
   - In the site's own voice: no "should" or "must", no em dashes (use "-"), and no words that suggest wrongdoing, even when denied. `tools/check-voice.js` enforces this.
   - Name no individuals or journalists. Use drawn, faceless figures only.
   - Never rank or score countries, cities, governments, organisations, languages or tools.
   - Be ready to say sorry and correct (/corrections/).
6. **Keep data and existing content as they are** unless asked. Never delete content without asking.
7. **Accessibility and speed.** Semantic HTML, keyboard access, AA contrast, tap targets of at least 24px, no sideways scroll at 390px, and fast on 3G.
8. **Funders.** Wellcome and every other funder stays in the funder records. Do not mention Wellcome in evidence briefs.

## Every change
1. Edit the source (data, builder or page script), never only the generated HTML.
2. Build with `node tools/build-static.js`.
3. Run the checks: `git add -A`, then `node tools/check-all.js` (or `npm run check`). It runs every check in `tools/checks.js` in order and prints one summary; `--list` shows what each guards, `--fast` leaves out the slow browser checks (a partial run, never a full pass) and `--only name,name` runs a few. It starts the local server on port 8765 for the contrast and target checks when nothing answers there. It never stages files: the site check reads tracked pages only, so it reports "incomplete" while pages are untracked (`--stage` stages them for you). A deliberate change in page weight is recorded by hand with `node tools/check-weight.js --update`. A new `tools/check-*.js` goes into `tools/checks.js`, or into its EXCLUDED list with a reason, or check-all fails. On GitHub, `check-data.yml` runs the same list with `--fast` on every push and pull request, with no path filter (Node 22; the workflows pin actions/checkout and actions/setup-node by commit SHA, with the version in a comment), so the three browser checks stay a local step.
4. When styles.css or a script changes, bump the cache version `?v=N` across all HTML and JS.
5. Commit with a clear message, push to the session branch, open a PR, merge, then fast-forward the branch. Never force-push. Never run git stash or pull while a film render is writing files. Do not push while a workflow that commits its results back is running (`verify-sources.yml`, `verify-urls.yml`, `city-districts.yml`, `city-history.yml`, `date-sources.yml`, `heat-news.yml`, `evidence-weekly.yml`): its push fails if the branch has moved. Wait for its commit, then fast-forward.

## Code and data conventions
- When the documentation and existing code disagree, follow the code's conventions, and in your final reply, list all the inconsistencies you found.
- Page scripts are IIFEs with "use strict". Builders pass their data in as `window.X` JSON. With no JavaScript, the page still shows its content.
- Where a page and `llms-full.txt` say the same thing, one `tools/*-text.js` module holds the words for both (named in each section below), so they never differ.
- AI may prepare drafts, records and proposals; a person approves before anything is published, and no AI pass stands in for a human reviewer or second coder.
- Long lists use `content-visibility: auto` (`.sol-group .sol`, `.rf-card`, `.refs__list li`, `.sg-card`, `.hr-rec`); keep each `contain-intrinsic-size` near the median item height at 390px.
- Reuse the existing classes (`pg-hero`, `hub-*`, `sol-bar`, `lv-*`) and colour tokens (`--ink`, `--orange`, `--ember`, `--line`). Match the visual style.
- **No accent stripes.** A thick coloured edge down one side of a card, note or tile reads as template filler (the owner's decision, November 2026). Use a hairline border all round, a light tint of the colour and a text label that carries the meaning; `node tools/unstripe.js <selector>` does the rewrite. Section rules above headings, legend keys, connectors, menu and selection states, thin neutral quote rules, the pop-ups, printed handouts and films are allowed; the list and the reason for each is in `tools/stripe-rules.js`, and `tools/check-stripes.js` (also run on GitHub) fails on anything else.
- **Four shared shapes for boxes** (the owner's decision, November 2026): a card (`.cs-card`: white, hairline, `--r-md`, `--pad-std`, flat), a note (`.cs-note` with `--limit`, `--watch` or `--example`, and a `.cs-note__label` that says what it is), a row (`.cs-row`) and a feature panel (`.cs-panel`). Use them for new work rather than a new one-off class. Every box keeps to one scale: corners `--r-sm`, `--r-md`, `--r-lg` (or a pill), fills white, `--canvas` or `--sand-50`, padding `--pad-compact`, `--pad-std` or `--pad-roomy`, and no drop shadow unless it floats (sticky bars, hover and open states, map controls). The scale is in `tools/card-rules.js`; `tools/normalise-cards.js` snaps old styles to it; `tools/check-cards.js` (also run on GitHub) fails on drift.
- **Seven type roles** (the owner's decision, November 2026): display (Anton capitals: page titles and the homepage's story heads only), section heading (Hanken bold `--fs-22`), subheading and card title (Hanken bold `--fs-18`), body (Hanken `--fs-16`, line-height 1.55), secondary (`--fs-14`, 1.5), label (bold capitals `--fs-12` with `--label-track`) and editorial (Newsreader, for ledes and quotes, not headings). Nothing is smaller than 12px. Line-heights are 1.15 (headings), 1.4 (interface) or 1.55 (body). The scale is in `tools/type-rules.js`; `tools/normalise-type.js` and `tools/heading-voice.js` snap old styles to it; `tools/check-type.js` (also run on GitHub) fails on drift.
- **Colour has one meaning each** (the owner's decision, November 2026): ink and two greys (`--grey-700`, `--grey-500`) for text, `--line`/`--line-strong` for hairlines; `--orange` for brand and action (buttons, link underlines); `--ember` for heat and harm (what drives a cycle, limits); `--break` for a fix (what breaks a cycle, examples); `--amber` for caution. Evidence strength uses one scale on every page (`--ev-strong`, `--ev-mid`, `--ev-limited`, `--ev-guide`), whatever words each feature uses. Links take the colour around them with an orange underline. All text meets WCAG AA. The palette is in `tools/colour-rules.js`; `tools/normalise-colours.js` snaps old styles to it; `tools/check-colours.js` (also on GitHub) and `tools/check-contrast.js` keep it.
- **The opening and the header** (the owner's request, November 2026): read `docs/homepage-opening.md` before touching either. Fixed points: the homepage opening uses five colours only (`--ink`, `--canvas`, `--orange`, `--grey-500`, `--line`) and the spacing scale `--s-1` to `--s-8`, with no gradients, glows or grain; in the header Signals is green (the owner's choice), the map is an ink outline and Start here is filled orange; the header fits itself (`csn--f1` to `csn--f9` in `tools/site-nav.js`) and wraps rather than overlapping; the brand, Start here and Menu are never hidden. The opening's styles are the last two blocks of styles.css.
- **Reflow at large text** (November 2026): no page scrolls sideways at 320px with text at 200% (WCAG 1.4.10); `check-site.js` has a third pass for it. The shared header CSS (`tools/site-nav.js`, on every page) and the end of styles.css let long words wrap (`overflow-wrap`; headings `anywhere`), keep selects and inputs within their box, and table cells at `break-word`. For new layouts: give grid tracks `minmax(0, 1fr)` or `minmax(min(100%, Npx), 1fr)` rather than a fixed px minimum over 288px, let flex rows of labels wrap, avoid `white-space: nowrap` on anything longer than a word or two, and put wide tables in a scrolling wrapper with `role="region"`, an `aria-label` and `tabindex="0"`.
- **Touch targets** (interaction audit, November 2026): every standalone link, button or control has a tap area of at least 24px, or sits far enough from its neighbours (WCAG 2.2, 2.5.8); aim for about 44px on phones. Grow a small target with an invisible layer so nothing moves (`position: relative` and an `::after` with `position: absolute; inset: -10px -4px`, as in the "Tap areas" rules in styles.css). Links inside a sentence, the drawn map points and the pop-ups are exempt. `tools/check-targets.js` keeps it.
- **The site's own visual style decides.** Design skills (Refero, Emil Kowalski's set and others in `.claude/skills/`) advise on craft. They never override the site's existing classes, colour tokens, type, layout patterns or voice, and outside references never replace them. Where a skill and the site's style differ, the site's style wins.
- IDs are stable and never renumbered. Each source has a label or title and a url.
- Every data widget handles loading, no network, error and empty states. Add a check for any calculation or import.
- A lever can carry `watch`: documented side effects, each with sources. They show as "Watch for" on the map, on /actions/ and in llms-full.txt, and `build-data.js --check` checks their format. Research batches that deepen the map use the pattern in `research/2026-11/gap-lenses/`: a patch file per batch, `audit.js` to check every number against its checked source, and `apply.js`, which refuses unconfirmed sources, missing ids and duplicates.
- Homepage story: each open section (`HOME_OPEN`) uses the `.story` anatomy (eyebrow, `h2.story__h`, lede, one focal point, one action, a `.story__more` fold) and its act tone. Homepage numbers sit in `data-stat` spans that the build fills from data. Only the ticker and click-driven animations loop. `build-data.js --check` enforces all three.
- Keep each change to what was asked. Prefer targeted edits to rewrites.

## Signals
`/signals/` follows developments outside Common Shade: commitments, findings, gatherings and guidance on heat. One canonical record per initiative lives in `data/site/signals.json`; the model is `tools/signals-model.js`, shared by the page (`tools/build-signals.js`), the text twin and llms-full.txt (`tools/signals-text.js`), the checks and the tools.
- A commitment is tracked deliverable by deliverable (an office, a rule, a fund, a plan), each with dated milestones (`announced`, `adopted`, `effective`, `funding-announced`/`-committed`/`-disbursed`/`-spent`, `delivered-partial`, `delivered`, `implementation-observed`, `evaluated` with its findings) and world events (`superseded`, `cancelled` and so on) in its history. Only an `effective` milestone may be future-dated, marked `scheduled`. Each piece of evidence names a source by its stable id, what it establishes and the terms the source check found.
- Evidence states are derived, never typed, from `data/site/signals-checks.json` (written by `node tools/signals-sync.js` from `data/inbox/*/link-check.json` content checks and research link checks): checked against an original, reported by secondary sources, or not verified. A page that only opened is not evidence. Evidence at one step never fills earlier steps; an effective date passing shows no compliance; an evaluation is not proof of cause; missing evidence is "not verified", never "failed" or "stalled".
- `stage` and `history` in each commitment are derived for older readers of the file: after editing, run `node tools/signals-sync.js` (it also re-serialises the file). Heat relevance is `explicit` or `interpreted` with a note; a `reading` is labelled interpretation and reviewed. Every record has `review.reviewed` and `review.due`. An event watch (the COP31 group) has a scope, a cut-off and dated check-ins that link to records; its closing synthesis is written only after review.
- **Page shape (November 2026).** The page opens with "What moved": steps dated in the last 45 days (when they happened, never when they were added), dated steps coming up, and ways to follow. `tools/signals-feeds.js` builds that strip and writes `signals/feed.xml` (Atom, one entry per record) and `signals/calendar.ics` (scheduled steps and the next El Niño bulletin). Only the 8 newest cards are on the page; the rest are in `signals/cards.json`, which `signals/signals.js` loads when a reader filters, searches, opens a view, prints, downloads, follows a link to an older record or asks for them all (with a stated failure state). An index of the older records keeps their anchors on the page, and `/signals/all/` lists every record for readers without JavaScript. `tools/check-signals.js` checks all of this.
- **Connected (November 2026, phase 2).** Each checked piece of evidence shows the checked page's own sentence holding its longest term ("From the checked page"); `tools/signals-sync.js` writes these `passages` into `signals-checks.json` from each batch's `_excerpts.json`, keeping only prose and tidying only page furniture. A commitment's record opens with its dated path. `tools/signals-context.js` puts "What is moving here" on every country and city page (a city shows its country's records; none reads "not tracked here yet", describing the records, not the place) and a "Moving now" line under each action on /actions/.
- **Wider (November 2026, phase 3).** Each open deliverable shows its next step on the card ("Next step, as the sources describe it": the deliverable's own `next`, and who made the commitment, `holder` if set, else the record's `who`); no one is named for a step not reached. `.github/workflows/signals-weekly.yml` runs `tools/signals-harvest.js` every Monday: free feeds (ReliefWeb through its API, which needs the approved app name in the `RELIEFWEB_APPNAME` secret and is skipped with a note without it; PreventionWeb, UN News, WHO) read on GitHub only, leads that mention heat and a covered place, not already tracked or proposed, in `data/signals-candidates/<date>.json` with a review pull request. Leads are never evidence; a proposed lead becomes a record only through a research batch. A lead marked `context` (how the heat season is going: alerts, closures, people affected; the owner's choice for ReliefWeb, November 2026) never becomes a record: `sof-review.js new` and `ladder` list those in the briefing month's draft, for the editor only. The coverage grid ("Where records are") lists every searched place alphabetically with its records and the last search date; a low number describes the records, not the place. Translations of the briefing are not planned (the owner's decision: English only, November 2026).
- Maintenance: `node tools/signals-review.js due` (records due, passed effective dates, milestones not checked against an original), `sources <id>`, `propose` and `apply` (refuses evidence the source check has not confirmed and needs an approver). Edge cases with no real record yet (mixed or negative evaluations, supersession, corrections) are tested on fixtures in `tools/check-signals.js`, never as published data. The migration that introduced this model is `research/2026-11/signals-rebuild/migrate.py`.

## State of the field
`/whats-new/` ("State of the field") is a monthly briefing built around one argument. It differs from the pages around it: Signals follows each development on its own, Growing records changes to Common Shade, and the evidence map examines the knowledge base. `/whats-new/` shows the latest published edition in full, with the archive. Each edition also has a stable page, `/whats-new/<YYYY-MM>/`, with a Markdown `briefing.md` beside it. `tools/build-sof.js` builds them, the model is `tools/sof-model.js`, and `tools/sof-text.js` holds the words the page, the briefing and llms-full.txt share.
- **Edition files.** A published edition is `data/site/briefs/<YYYY-MM>.json` (schema 2); a draft is in `data/site/briefs/drafts/`.
  - Drafts preview only in `research/sof-preview/` (git-ignored), and `_config.yml` keeps the drafts folder off the served site.
  - A month passing never creates an edition, and an old edition says so once the following month has ended.
- **Contents.** An edition has:
  - one argument with what it rests on
  - up to three developments
  - an optional opportunity (roles marked as a proposal) and an open question (revisiting an earlier one only where it exists)
  - a forward look, one question for each kind of reader, a short note on Common Shade, sources and revisions
- **Dates.** Every development keeps when it happened apart from when it was reviewed; anything outside the reporting period carries `why_here`.
- **Claims.** Each claim names a source, what it establishes and what it does not.
  - "Not found" states what was searched.
  - Sources that were not content-checked are marked.
  - No step may go further than the linked Signals record shows.
- **Sources are snapshots** (`node tools/sof-review.js snapshot`): title, date, url, the source check at the time and a fingerprint of the record. A later change to the knowledge base shows beside the edition; it is never written into it.
- **Preserved at publication.** `data/site/briefs/_ledger.json` holds each published edition's hash at its latest revision. A change needs a dated revision, plus a /corrections/ entry for a correction, then `seal`. The October 2026 edition keeps its first text in `as_published` (one funder's name removed on 16 November 2026, marked where it was).
- **Reach (November 2026).** Each edition shows three reading depths (word counts from the edition), a chat version ("Copy for WhatsApp" and an "Open in WhatsApp" link; `chatText()` in `tools/sof-text.js`) and its own share image, `whats-new/<YYYY-MM>/card.png`, rendered by `node tools/sof-card.js` (run by `publish`) and used as the page's og:image. `/whats-new/feed.xml` is the editions feed. `data/site/briefs/_next.json` names the next planned month and period; it shows on /whats-new/ until that edition is published, and never creates one. None of this changes an edition's text or ledger hash.
- **Continuity (November 2026, phase 2).** `new` (and `ladder <YYYY-MM>`) gives a draft `from_signals`: every Signals step dated in its period, steps scheduled in the month after, and weekly leads marked `context` published in the period (`season`), shown in the draft preview for the editor and removed by `publish`. Each edition offers "Read it as" for the four reader groups (its own question and where to start, `ROLE_LINKS` in `tools/sof-text.js`, kept in `?role=` and the browser). /whats-new/ lists "Questions so far": every question asked and what later editions found (`questions()`), also in llms-full.txt.
- **Promised and lived (November 2026, the owner's choice from the December 2026 edition).** An edition may carry `side_by_side`: up to six rows, each a covered place, setting a step in a commitment (a Signals or knowledge-base record) beside how the heat season went there (a source dated in the period, staged in a season batch `data/inbox/<YYYY-MM>-season/` and cited as `batch:<batch>/<id>`), with limits. The page, briefing and preview say side by side is not cause and effect (`PAIR` in `tools/sof-text.js`); `M.validate` enforces the rules and `check-sof.js` tests them on fixtures. The draft's `from_signals.pairs` lists, place by place, the period's Signals steps beside the context leads.
- **Workflow:** `node tools/sof-review.js new | snapshot | ladder | check | publish | seal` (step 10 of `/monthly-heat-update`). The owner approves every edition.
- The baseline and results of the November 2026 rebuild are in `research/2026-11/sof-rebuild/README.md`.

- **Model and rules.** `tools/funding-model.js` loads the records and attaches the source check. `heat-economy/funding-core.js` holds the rules shared by the build, the page script (`heat-economy/money/funding.js`), the harvest and `tools/check-funding.js`. `tools/build-funding.js` builds the pages (called by build-economy.js), the CSV files, the llms text and the "Funding and opportunities" blocks on topic pages (`CONTEXT`, injected at the end of build-static.js). `tools/funding-text.js` holds the shared words.
- **Evidence.** Every key fact names a source key and a term. Sources are in `research/2026-11/funding-opportunities/sources.js`, staged by `stage.js` and checked with `verify-sources.yml` (`month: 2026-11-funding-opps`). A record is published only when its core terms were found; the rest are held back and named in the build output. Aggregators and social posts are discovery only.
- **Status.** Application status (upcoming, open, deadline day, rolling, closed, withdrawn, unknown) and verification (verified, review due, source unavailable, conflicting information) are computed and kept apart; "verified open" needs both. A future deadline is not proof a call is open, no deadline is not rolling, a date-only deadline never reads "open" through its day, and each round is its own record. The source-check date is shown as "Source checked", never the build date.
- **Distinctions.** A funder is not a call; a programme budget is not an award; procurement, equity and debt are not grants; an individual consultancy is not a tender; a fee-charging course is not a funded fellowship. Relevance is explicit, related or potential, and potential is never shown as confirmed eligibility. There is no "Apply now" on a funder profile, no fit score, and no hidden eligibility guess: a call excluded by a reader's filter is counted and can be shown.
- **Upkeep.** `.github/workflows/funding-weekly.yml` runs `tools/funding-harvest.js` every Wednesday. It reads the public feeds and APIs in `data/funding/registry.json` and opens a review pull request with candidates and status changes; `--dry-run` prints the counts only. The October 2026 programme list was audited (`research/2026-11/funding-opportunities/legacy-audit.json`). The shortlist is kept in the reader's browser only.

## El Niño pages
`/el-nino/`, `/print/el-nino-briefing/`, `/el-nino-and-cities/`, the El Niño watch on `/signals/#el-nino-watch` and the El Niño route on `/heat-tools/#el-nino` share one outlook record, `data/site/enso-outlook.json`, read through `tools/enso-outlook.js`.
- **One record, one wording.** Each bulletin keeps its issuer's date, forecast period, index and thresholds; bulletins are never averaged, and superseded ones move to `history`. `facts()` returns the sentences every page repeats (status, phase and strength odds, the historic-event chance, the reading, the local limits), so no probability is typed into page words. `validate()` refuses broken dates, a cross-year period without both years ("November 2026 to January 2027"), probabilities outside 0-100 or not adding up, and strength bands added to the El Niño total instead of sharing it.
- **Four kinds of statement stay apart:** observed (with the period and whether a figure is weekly or three-monthly), forecast (with its period), Common Shade's reading, and local uncertainty. ENSO is context for months-ahead preparation, never the trigger for local action.
- **Evidence:** claims live in `research/2026-11/enso-asia/` and `research/2026-11/enso-update/` (each with `claims.json`, `gate.js`, `confirmed.json`); the build stops on an unconfirmed claim. A failed fetch changes nothing: the last verified bulletin stays, and once its next date passes the pages say the new one is due and not yet checked. Updating is prepared, not automated: stage the new bulletin, run `verify-sources.yml` and the gate, move the old entry to `history`, edit the record, rebuild. The log is `research/2026-11/enso-update/CHANGELOG.md`.
- **Tools:** the route's records come from `research/2026-11/heat-tools/additions-enso.json`, merged by `apply.js` only when their provider facts passed the check; each states its decision, lead time, update frequency and product kind (bulletin, dashboard, forecast service, warning service, workbook). Nothing builds a local heatwave predictor from ENSO odds.
- `tools/check-enso.js` checks the record, fixtures, the identical sentences across pages and llms-full.txt, anchors, the journey links and the print sheet.

## How heat is reported
`/how-heat-is-reported/` reads two collections of news articles on heat in South and Southeast Asia. Its argument runs in three steps: a first reading of the curated collection, what the multilingual pilot found, and the sharper question the two raise together (does coverage follow protection from a named responsibility, through money and delivery, to results?). `tools/build-media.js` builds it, with the model in `tools/media-model.js`, the page script in `how-heat-is-reported/media.js` and the page's own stylesheet in `how-heat-is-reported/media.css`.
- **Two canonical sources, never copied into components:**
  - the curated collection, `research/2026-10/media/extreme-heat-journalism-2018-2026.csv`, read at listing depth; its `ID` column (`b00`...) is stable and never renumbered
  - the pilot, `research/2026-10/media/pilot/articles.json` and `exemplars.json`, read in full text and coded once, without a second coding
- **The editorial layer**, `research/2026-10/media/editorial.json`, holds:
  - definitions and review depths
  - the ten examples and their suggested follow-up questions
  - the comparisons, where every cell quotes its record's reviewed field exactly
  - the question kit (topics, kinds of public record, perspectives, what to verify)
- **Records:** one per unique URL. A story in both collections is one record with both memberships; publication records and unique records are counted apart.
- **Nothing is inferred to fill a filter.** A record read at listing depth has no trail, cycles or population, and the page says "not assessed". A format is recorded only from the pilot coding or the collection's link type.
- **Reporting trails** use four states: described in the reviewed material, explicitly reported as unknown, not found in the reviewed material, and not assessed. They never imply failure or omission.
  - Keep what an article reports, what its cited research establishes, Common Shade's reading and open questions apart.
- **Downloads:** `records.csv` and `records.json` (every unique record), the collection CSV as first published, a filtered CSV built in the browser from `records.csv`, and a Markdown reporting brief. The explorer's filters, comparison (`cmp`) and kit (`kit`) live in the address.
- **Old anchors still land** (listed and checked in `tools/check-media.js`).
- **What stays open, and how it shows:**
  - Links: `verify-urls.yml` on `research/2026-11/media-rebuild/urls.txt` writes `link-status.json`. The page says "opened" or "could not be checked automatically" (never "verified" or "dead") and dates the check from that file's commit.
  - Translations: national-language titles read "working translation, not yet reviewed by a speaker of [language]". `translation-review.csv` is the sheet for volunteers, whose reviews come in through the join form and are credited in aggregate, with no names.
  - Codebook: `pilot/working-definitions-as-applied.md` is generated from the records (never by hand). It cites record ids, not passage locations, which can name people.
  - Second coding: `pilot/second-coding-protocol.md` is proposed, not scheduled.
- The baseline and results of the November 2026 rebuild are in `research/2026-11/media-rebuild/README.md`.

## City heat, districts, history and the Atlas
The build record (steps 1 to 6, with how each was made) is in `research/2026-11/city-heat/README.md`; the build brief, `BUILD_BRIEF.md`, is done or closed (step 5 closed with no what-if view, and Hanoi's districts are held back), and its "Stop and ask the owner" list still applies. Lasting rules:
- **Heat today** (`city-heat/city-heat.js`, words in `LIVE_WBGT`): an estimated heat stress (WBGT) from one Open-Meteo request, and NEA's measured WBGT for Singapore, labelled as a measurement. The formula is the Australian Bureau of Meteorology's approximation in `city-heat/heat-core.js`; `script.js` keeps one copy, and `tools/check-city-heat.js` checks that the two agree and that the constants match the checked source in `data/inbox/2026-11-city-heat/`. No heat-stress level is shown beside the estimate.
- **Cities and profiles:** profiles are build-only (`CITY_PROFILES`); the homepage city view loads `/cities/profiles.json` only when a reader nears it. A new city cites only sources that passed the check in `data/inbox/2026-11-city-heat/` (`research/2026-11/city-heat/batches.json`). Map labels place themselves and hide where they would collide; the city buttons and lists still name every city. The cities film keeps its caption "The first twelve cities" on purpose (`watch` in `tools/explainers/site.js`).
- **What heat costs here** (`cityBrief()` in `tools/build-static.js`): a checked cost figure only where the profile names one, otherwise "No checked estimate found yet".
- **Districts** (`cityDistricts()`, `city-heat/districts.js`, `.github/workflows/city-districts.yml`): a table that loads when opened, each figure marked above or below the middle district, never ranked. WorldPop figures are modelled, not counted; clinics are in the data but not shown. Read new figures against known totals before publishing.
- **Heat over time** (`cityHistory()`, `tools/city-history/`, `.github/workflows/city-history.yml`, checked by `tools/check-city-history.js`): a NOAA station first, with ERA5-Land only as regional background. A year counts with at most 15 missing days and 3 in any month; a station needs 80% of years and 5 valid years in each end decade; it sits within 35 km of the centre, and a city never borrows a neighbour's. `stationBreak()` withdraws a measure after a step change at the station; a withdrawn measure keeps its chart, with the break year and the reason beside it (Bangkok's daytime trends, see /corrections/). Cities without a passing station say so on their page.
